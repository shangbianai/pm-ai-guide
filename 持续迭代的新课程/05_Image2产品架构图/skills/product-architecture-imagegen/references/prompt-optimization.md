## 1. 输入解析

把用户自然语言整理成 `Architecture Brief`：

- 产品名称与一句话定位
- 目标受众：高管、客户、产品、研发、运营或监管
- 核心用户/外部角色
- 关键价值流或业务闭环
- 产品渠道与多端入口
- 核心业务能力
- 应用/平台服务
- 数据来源与数据资产
- 模型、算法或智能体能力
- 技术基础设施
- 治理、合规和运维
- 明确不在范围内的内容

不要把 UI 页面、业务能力、微服务和数据库混在同一层。每层保持一致的抽象级别。

## 2. 架构分解

默认使用以下自下而上的分解阶梯，并根据产品删减：

1. 硬件与基础设施
2. 技术平台与中间件
3. 数据采集、处理与资产
4. 模型、算法或智能引擎
5. 平台公共服务或智能体编排
6. 核心业务能力
7. 产品应用与渠道
8. 用户角色与业务价值
9. 跨层治理、合规、可观测性与运营

多边平台优先明确角色、交易对象和交互关系；AI 产品优先明确数据、模型、编排、工具调用、人工接管与评测闭环。

## 3. 信息不足时的处理

- 能根据领域常识补齐时，生成有用草案并将新增内容标注为“假设”。
- 会导致产品边界完全不同的缺失信息，最多询问 1 至 3 个问题。
- 不虚构具体公司、合规认证、系统接口、数据库品牌或业务指标。

## 4. Image 2 提示词结构

按照以下顺序组织最终提示词：

```text
Use case: infographic-diagram
Asset type: 16:9 产品架构商务汇报图
Reference image: style-XX，仅作为视觉与构图参考；不要复制其中的产品内容。
Primary request: 产品定位与架构任务。
Audience: 目标受众与用途。
Canvas and style: 画布、主题、字体、配色、材质、空间关系。
Composition: 套用所选风格的构图规则。
Architecture layers/domains: 每层名称、模块与角色。
Relationships: 只保留有业务含义的箭头，使用动词。
Governance: 跨层治理内容。
Text constraints: 要求逐字准确、水平可读。
Avoid: 明确禁止跑偏的视觉元素。
```

给图片生成模型的模块数量建议：每个视觉组 3 至 7 项。超出时先合并同类项，详细清单保存在交付提示词中，不要强塞进一张图。

## 5. 文字与视觉约束

- 中文标签通常控制在 2 至 8 个汉字。
- 通用缩写保留英文，例如 AI、API、CRM、GPU、CPU、RAG、ETA、GIS、IoT。
- 所有文字使用引号或明确列举，并要求逐字渲染。
- 文字必须水平、正对观众、位于模块内部或紧邻模块。
- 参考图只控制构图、配色、形态、线条与视觉密度；产品名称、模块、角色必须替换为用户内容。
- 不生成水印、Logo、虚假指标、重复模块、无意义装饰箭头。

## 6. 质量验收

生成后检查：

1. 产品名称和关键中文是否正确。
2. 用户/角色、渠道、能力、数据、技术、治理是否各在正确层级。
3. 箭头是否有明确方向和关系动词。
4. 所选编号的构图特征是否被保留。
5. 是否出现参考图中的旧产品内容残留。
6. 是否存在文字重叠、乱码、重复模块或不相关装饰。

若只有一处明显错误，使用单一目标的编辑提示词迭代；不要同时改变内容、布局和配色。
