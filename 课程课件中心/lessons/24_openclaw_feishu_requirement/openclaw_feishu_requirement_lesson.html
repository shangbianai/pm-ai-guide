用龙虾做需求管理：一句话新增需求

产品经理不一定随时在表格前，但需求会随时出现。我们要把一句话、一个反馈、一个临时想法，自动转成结构化需求，并同步到飞书需求池。

WHY

为什么这件事值得做？

很多需求不是在正式会议里产生的，而是在客户吐槽、内部沟通、临时想法和群聊里冒出来的。

  • 手动录入：容易忘、容易丢、格式不一致。
  • 只有原话：后续还要重新判断真假、场景、优先级。
  • 没有同步：需求池、需求表、群通知之间割裂。

目标

让需求从“随口一句话”变成“可跟踪的一条记录”。

关键

不是只新增文本，而是同步完成提炼、分类和流转。

适合场景

用户反馈、客户拜访、销售转述、业务方临时需求。

PM 价值

减少录入成本，把精力放回判断和取舍。

ARCHITECTURE

整体链路：表单/消息 → OpenClaw → 飞书需求池

1

入口提交

用户反馈、群消息或表单提交，先写入飞书多维表格，生成一条原始记录。

2

OpenClaw Agent 处理

服务端调用 openclaw agent --agent main --message ...，让 Agent 根据方法论分析反馈。

3

结构化字段回写

Agent 把分类、核心痛点、优先级、回复草稿、解决方案建议写回飞书表格。

4

群聊通知

处理完成后推送到飞书群，带上记录链接，方便团队继续跟进。

BUS FLOW

总线原理：把输入、AI、飞书串成一条流程

这里的“总线”可以理解为一条自动化处理链路：每一步只负责自己的动作，但最终把自然语言需求变成可追踪的飞书记录。

入口接收

用户打开 http://115.190.184.176:3000，提交昵称、邮箱和反馈内容。

服务校验

server.js 接收 POST /api/feedback，校验内容和反垃圾字段。

创建记录

服务端调用飞书 Bitable API，先把原始反馈写入多维表格，拿到 record_id。

拼接方法论

buildMethodology() 把记录 ID、反馈内容、分类规则、优先级规则拼成 Agent 指令。

触发龙虾

命令行执行 openclaw agent --agent main --message ...，让 Agent 完成分析和回写。

同步通知

Agent 更新分类、痛点、优先级、回复草稿，并向飞书群发送带链接的处理结果。

核心理解：Node 服务负责“接入和触发”，OpenClaw 负责“判断和执行”，飞书负责“记录和协作”。

FIELDS

飞书需求池字段怎么设计？

字段设计决定了后续能不能排序、跟进、复盘。先让 AI 写“结构化字段”，再让人判断是否进入排期。

用户吐槽的内容保留原始输入
用户昵称 / 邮箱方便回访和沟通
AI 解析状态未处理 / 已处理
反馈分类功能需求、体验问题、Bug 等
核心痛点提炼真实问题
优先级高 / 中 / 低
AI 回复草稿人工确认后再发送
解决方案建议短期、中期、长期
回复状态待回复 / 已回复
METHOD

Agent 不是简单搬运，而是做一次需求澄清

服务端会把一套处理方法论和原始反馈一起发给 OpenClaw Agent，让它按固定规则输出。

分类

功能需求、体验问题、Bug 反馈、性能问题、其他建议。

优先级

核心流程受阻、多数用户、有截止时间时优先级更高。

痛点提炼

不复述原话，而是挖掘背后的真实需求。

回复草稿

共情开头、明确表态、给出临时方案和后续通道。

SUMMARY

回顾重点：这节课的价值

这节课的重点不是“多一个表单”，而是把需求采集、AI 提炼、飞书沉淀和团队通知连成一条自动化链路。

  • 需求入口更轻：一句话也能进入需求池。
  • 结构更稳：分类、痛点、优先级自动补齐。
  • 协作更顺：飞书表格和群通知同步更新。
  • PM 更省力：把重复录入交给 AI，把判断留给人。
