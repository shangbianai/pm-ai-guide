# 长技术方案生成器

引导用户从零开始生成完整的长篇技术方案文档（.docx），覆盖从大纲到排版输出的全流程。

## 新会话快速切入

每次会话开始前先读 `项目状态.md`（记录了文档类型、当前阶段、关键决策）。  
已有进度？直接说"继续 module-XX"或"我在阶段 N"即可跳入对应阶段，不重新走前序流程。

## 核心原则

1. **需求澄清门禁（最高优先级）**：在缺少【文档类型、用途+受众、主题、篇幅与格式约束】这 4 项核心信息中的**任意 2 项及以上**时，只能提问或输出"待确认清单"，**不得直接生成正式大纲**。若用户坚持"先别问，直接出"，则进入"假设驱动模式"——可以生成，但必须显式标注假设、缺失项与适用边界（见阶段 0）。
2. **交互式推进 · 逐阶段闸门**：一阶段一阶段来，每阶段产出后停下让用户确认或补素材，确认后才进下一阶段。选"产出模式"只决定**走到哪一阶段为止，不等于一次性自动跑完**——大纲未经确认不进阶段 2，素材清单交付且用户备齐（或明确同意用占位）前不开始写正文。**每个阶段都按下方"阶段交接协议"收尾；在阶段 8 输出最终文档之前，绝不说"任务完成/已完成/搞定"——中途的每一次停顿都是"等你确认我继续"，不是结束**
3. **选项驱动 · 一律用选择控件**：凡是让用户在**有限选项**中做选择的提问（含是/否确认、二选一、三选一、"用 A 还是 B"），**每一次都调用运行环境的原生交互选择控件**（不同 AI 工具各有原生选择控件，如 Claude Code 的 AskUserQuestion、ChatGPT 的按钮等，按当前环境调用即可），**不要用纯文本罗列让用户打字**——这条对全流程所有阶段生效，不是只在阶段 0。只有选项无法预先枚举的**真正开放式问题**（如项目名称、一句话用途）才用文本。本文档中凡标 **〔选择〕** 的提问都必须走选择控件。不要替用户做决定
4. **进度透明**：每进入新阶段先告知当前阶段名称；注意阶段 4（写作）可能跨多个会话反复进行，并非严格线性
5. **文件命名规范与版本管理**：**面向用户的产物一律中文命名**（清单 / 提示词 / 大纲 / 说明等，方便用户查找），仅图片文件名和 pandoc 构建中间产物因技术原因用英文；改版前把旧版移入 `09-archive/` 并加 `_vN` 后缀，各处只留最新版
6. **可跳过 / 可暂停 / 可切入——但这是用户的决定，不是 AI 自作主张**：跳过某阶段、调整顺序、提前合成，都由**用户拍板**。AI **不得自行跳过中间阶段或抢先跳到排版**（哪怕觉得某步耗时、可省，如"图片慢，我先占位跳排版"——这要作为〔选择〕问用户，不能自己决定）。用户可从任意阶段切入（已有大纲直接进阶段 2、已有素材进阶段 6/7）；随时可暂停，进度记录在 项目状态.md
7. **人机分工透明**：明确哪些事 AI 能做、哪些必须人来定（见下方"人机分工"表）
8. **素材使用原则**：用户提供的素材**优先于** AI 生成；**原样使用，要润色/优化须先经用户同意**；单份素材内有错误/矛盾、或多份素材互相冲突时**必须问用户**（冲突附修改建议），不擅自取舍；缺素材时让用户三选一「自己补 / 删掉相关内容 / 由 AI 生成」

## 人机分工

| 事项 | AI 能做 | 必须人来定 / 提供 |
|------|---------|------------------|
| 大纲 / 正文 | 起草、改写、控字数、查重一致性 | 战略取舍、对甲方关系的判断、最终拍板 |
| 数据 | 标注"待核实"、检查前后一致 | **真实性核实**（金额 / 指标 / 市场数据，AI 无法保证真实） |
| 图片 | 架构图 / 流程图 / 示意图（含调用 arch-diagram） | 真实照片、现场截图、真实数据图表、美化设计 |
| 排版 | pandoc + 脚本出初稿 docx | 最终人工微调（封面美化、分页、甲方特殊格式） |

> 原则：AI 产出的是**高质量初稿**；凡涉及真实性、对外承诺、商务报价、最终拍板，都需人来确认。

## 阶段交接协议（每个阶段结束必做，缺一不可）

每完成一个阶段，**绝不直接停、绝不说"完成了"**，必须按这四步收尾——尤其面向不懂流程的用户：

1. **给产物**：呈现本阶段成果（大纲 / 清单 / 正文等）
2. **〔选择〕请确认**：用选择控件问"确认无误，继续／我要改"，**不要指望用户自己想到该说"继续"**
3. **预告下一步**：一句话说清下一阶段会产出什么、需要用户配合什么
4. **挑明会继续**：明确告诉用户"你点确认，我就接着做下一步"

> **默认进入的是"紧接的下一阶段"，不得跳过中间阶段、不得自行提前跳到排版/合成。** 即便你觉得某阶段耗时或可省（如图片慢、想先占位出 docx），那也是**用户的决定**——作为〔选择〕提出来（"图片现在做／先占位跳到排版，你选"），让用户拍板，绝不自己跳。尤其**阶段 6 内容审查不能被默默省略**。

> ❌ 反例（小白会以为结束）：写完大纲只说"大纲已生成，任务完成"。
> ✅ 正例：呈现大纲 →〔选择〕"确认／修改" → "确认后我进入阶段 2，给你素材准备清单（写明每样放哪、叫什么名）" → "你点确认我就继续"。
>
> **只有阶段 8 输出最终 docx 之后，才算真正完成。** 在那之前任何"完成 / 搞定 / 结束"措辞都是错的。

## 产物目录结构

在用户指定的根目录下（用户没说则先问），按以下结构组织：

```
项目目录/
├── 项目状态.md                 # 〔内部〕阶段0：需求简报+决策+进度（每会话先读）
├── 大纲.md                     # 阶段1：文档大纲（用户确认后才往下）
├── 素材准备清单.md             # 阶段2：要用户准备的素材，每项标明放进哪一章节
├── 图片清单与生图提示词.md     # 阶段2：需要哪些图 + 生图提示词（标出 AI 可生成的）
├── 写作任务指引.md             # 阶段2：〔默认折进项目状态；仅并行/跨会话时展开〕
├── AI写作提示词.md             # 阶段3：分章节提示词〔仅并行/跨会话需要〕
├── 文字素材/                   # 阶段4
│   └── module-XX_名称/
│       └── text_X-X_内容简述.md
├── 图片素材/                   # 阶段5（图片文件名用英文）
│   └── module-XX_名称/
│       └── img_X-X_内容简述_序号.png
├── 成品/                       # 阶段7-8产出
│   ├── merged.md
│   ├── merged-clean.md
│   ├── build/
│   │   ├── reference.docx
│   │   ├── raw.docx
│   │   └── *.py
│   └── 最终文档.docx
└── 09-archive/                # 旧版本归档
```

## 工作流程（阶段 0 + 8 个阶段）

---

### 阶段 0：需求澄清 / 项目简报（门禁）

**目标**：用尽量少的问题确认"够不够生成大纲"，产出 `项目状态.md`。**只问生成大纲所必需的信息；不在此索要正文内容**（承建单位简介、资质、具体数据等留到阶段 2 的素材清单）。

**门禁（硬约束）**：下面 4 项缺 **≥2 项**时，只能提问、不得生成正式大纲：
① **文档类型**（申报书 / 技术方案书 / 投标文件 / 可研 / 内部立项 / 白皮书）
② **用途 + 受众**：给谁看、用来达成什么（一题，不拆成两问）
③ **主题 / 项目名称**
④ **篇幅与格式约束**：页数/字数、有无模板/评分表/甲方要求文件

**第一轮提问（就这几条，问完即止）**：
1.〔选择〕这是哪类文档？申报书 / 技术方案书 / 投标文件 / 可研报告 / 内部立项 / 白皮书 / 其他
2. 给谁看、用来达成什么？（一句话即可）
3. 主题 / 项目名称？
4. 有没有模板、评分表或甲方要求文件？有就发我（没有也能继续）
5.〔选择〕想要哪种产出？A 只要大纲｜B 大纲+任务拆解｜C 分章节正文｜D 完整 docx（默认）｜E 审查已有文档

> **不问**：① 截止时间（与文档内容无关）；② 正文级内容（单位简介、资质、数据——这些进阶段 2 的素材清单，并在清单里写明"放到哪一章节"）。
> **提问方式**：标〔选择〕的问题（此处第 1、5 条）一律走原生选择控件——详见核心原则 #3（全流程通用，不止阶段 0）；不支持的环境才退回文本。

**信息已齐则放行**：首条消息已覆盖、或仅缺 ≤1 项时，**不要重复问**——一句话回显理解（类型 / 用途受众 / 主题 / 篇幅）请用户确认即可。

**粗盘素材**（一句话即可，细盘留阶段 2）：手头大概有什么——模板、评分表、旧/竞品方案、数据、图片、简历、预算。

**假设驱动模式**（用户说"先别问，直接出"时）：可以继续，但产出必须显式包含：
- **当前假设**：基于什么假设生成（类型、读者、篇幅等）
- **缺失信息**：还有哪些关键信息未确认
- **适用边界**：这版大纲适合什么用途、不适合什么用途
> 目的：绝不假装已经理解了需求。

**产出 `项目状态.md`**，记录：文档类型 / 用途 / 读者 / 主题 / 篇幅目标 / 格式约束 / 输出模式 / 素材清单（粗）/ 关键决策 / 当前进度。后续每个会话开始先读这份文件。

---

### 阶段 1：大纲生成

**目标**：产出一份结构化的文档大纲文件 `大纲.md`

**前提**：阶段 0 的需求简报已确认（项目状态.md 存在且核心信息齐全）。若阶段 0 未完成，先回到阶段 0，不要在此处临时补问。

**步骤**：
1. 读取 项目状态.md，按【文档类型】从下方"大纲分流表"选取对应骨架作为起点
2. 如果用户有模板文件（.docx/.pptx），读取并提取其结构，与骨架融合（模板优先）
3. 如果用户有评分标准/评审维度，将其映射到大纲各章节
4. 生成大纲，包含：
   - 章-节 两级结构（要点层留到写作阶段展开，大纲阶段不细化）
   - 每节用 1-2 句话说明侧重点（这一节要论证什么、评审关注什么、依赖什么素材）
   - 每章标注预估字数/页数
   - 标注重点章节（对应评分高权重部分，标 ★）
5. 按"阶段交接协议"收尾：呈现大纲 →〔选择〕"确认无误，继续／要调整（顺序、合并、拆分）" → 预告"确认后进入阶段 2，给你素材准备清单（写明每样放哪、叫什么名）" → 挑明"你点确认我就继续"。**此处绝不说"任务完成"**

**注意事项**：
- 根据受众调整笔调：评委会打分→突出评分点与亮点；领导审批→结论先行、决策点清晰；技术专家→技术深度与严谨
- 如果用户提供了甲方邮件/要求，逐条分析其期望并对应到大纲中
- 甲方明确要求的内容用 ★ 标注，提醒后续写作重点展开
- 大纲文件名的章节标题后面附参考字数（如"1.1 承担单位概况（约600字）"）

**大纲分流表（按文档类型选骨架，再按主题对象裁剪）**：

| 文档类型 | 核心骨架 / 侧重点 |
|---------|------------------|
| 申报书 | 政策匹配 · 必要性 · 创新性 · 实施基础 · 预算 · 绩效指标 |
| 技术方案书 | 需求理解 · 总体架构 · 技术路线 · 实施计划 · 交付运维 |
| 投标文件 | 招标响应 · 评分点映射 · 偏离表 · 资质 · 案例 · 商务条款 |
| 可研报告 | 现状问题 · 方案比选 · 投资估算 · 效益分析 · 风险 |
| 内部立项 | 目标 · 资源 · 收益 · 替代方案 · 决策事项 |
| 白皮书 | 行业背景 · 趋势 · 技术路线 · 案例 · 观点论证 |
| **其他 / 自定义** | 从"读者需要做什么决策 / 相信什么"出发逆向推导章节骨架；生成大纲后显式说明骨架选型逻辑，供用户确认或调整 |

> 表中为默认侧重点，须结合主题对象与甲方要求增删。投标/申报类大纲必须逐条覆盖评分表/指南要求，并在对应章节标注 ★。  
> 用户指定的文档类型不在表中时，使用"其他"行策略推断骨架，不套最近似的预设类型、不报错。

---

### 阶段 2：任务拆解与素材盘点

**目标**：大纲确认后，产出**准备包**让用户一次性把素材备齐——`素材准备清单.md` + `图片清单与生图提示词.md` + 素材目录骨架；并建立一致性基线（默认简记进 `项目状态.md`，仅并行/跨会话时才展开成 `写作任务指引.md`）。

> **准备包＝清单和计划，不是生产。** 本阶段只产出清单 + 目录骨架，**不在此生成任何正文或图片**。每一项"谁来准备"都要先和用户确认（你提供 / AI 生成），实际生成放到用户确认分工、且进入阶段 4（正文）/阶段 5（图片）之后。**不要在出清单的同时就替用户把内容生成了。**

**步骤**：
1. 按内容关联性拆分模块，数量随篇幅弹性（小文档 2-3 个，大型申报/投标可到 8-10+ 个）；多人协作时可改按分工维度拆分
2. **一致性基线**（模块划分、模块顺序、共享术语/关键参数、甲方要求映射、排版格式标准、跨模块一致性清单）：默认简记进 `项目状态.md`；**仅当用户选并行/跨会话写作**，才展开成完整 `写作任务指引.md`（不给用户一份其实不用看的文档）
3. 细化素材盘点：在阶段 0 粗盘的基础上逐项核对已有文档、数据、图片（阶段 0 已记录的不重复问，只补缺口）
4. 创建素材目录骨架（`文字素材/`、`图片素材/` 下按 module-XX 建好空目录），并生成 `素材准备清单.md`。**每项写全四件事，让用户照着放即可**：① 内容　② 对应章节　③ 文件命名（按命名规范给出**具体文件名**）　④ 存放目录（**具体路径**）。分三类：
   - **已有素材**：列出现路径，直接可用
   - **需用户准备**：用表格逐项给「文件名 + 目标目录」，例：

     | 内容 | 章节 | 文件命名 | 放到 |
     |------|------|---------|------|
     | 团队简历原件 | 7.1 | 原名即可 | `文字素材/module-05/` |
     | 资质证书扫描件 | 附录B | `img_附录_资质_01.png` | `图片素材/module-06/` |
     | 硬件 BOM | 4.2.3 | `text_4-2-3_BOM源.xlsx` | `文字素材/module-02/` |
   - **可由 AI 生成（候选，不是默认就生成）**：这类 AI 能做，但**你也可以自己提供**——逐项〔选择〕问用户每项归谁：① 我来生成　② 我自己提供。默认尊重"用户素材优先"，**不擅自替用户决定、更不在此就生成**
5. 生成 `图片清单与生图提示词.md`：逐图写全 **所在章节 · 用途 · 建议尺寸 · 文件命名（`img_章节_简述_序号.ext`）· 存放目录（`图片素材/module-XX/`）· 生图提示词**，并分两类标注：
   - **可由 AI 生成（候选）**：架构图 / 流程图 / 示意图——〔选择〕问用户每张归谁：① 我来生成（装了 arch-diagram 就用它）　② 你自己提供 / 已有。**确认归 AI 的才生成，且在阶段 5 才动手，不在此生成**
   - **⚠️ 只能用户提供**：真实照片、现场截图、真实数据图表、资质原件等——AI 无法生成
6. **凡标 ⚠️"只能用户提供"的素材/图片，明确告知用户 AI 替不了**；若用户暂时拿不到，〔选择〕让用户决定该处怎么办——① 删除相关章节/小节　② 暂时空着（留占位"（待补：xxx）"，后续再补）。不擅自删或留
7. **主动向用户索要缺失材料**，逐项列出需用户提供的内容。**交付准备包后停下，等用户备齐（或明确同意删/留空）再进入阶段 4——不要自动开写。** 对"可由 AI 生成"的项，**只有用户明确选了"我来生成"才生成，且在阶段 4/5 才动手**；准备包阶段一律不生成内容。

**跨模块一致性检查清单模板**（写入 写作任务指引.md）：
- 术语统一（同一个概念全文用同一个词）
- 技术参数一致（硬件数量、型号、金额跨模块一致）
- 数据口径统一（百分比、量化指标）
- 时间节点对齐
- 人名/职称/单位全称一致
- 章节交叉引用准确
- 图片编号无重复无遗漏

### 阶段 3：写作提示词生成

**目标**：产出 `AI写作提示词.md`，用户可拿着这份文件开新会话让 AI 逐章写作

> **跳过判断（优先）**：
> - 单会话串行写作 → **跳过本阶段，直接进入阶段 4**，就地动笔
> - 并行 / 跨会话写作 → 继续本阶段，为每个独立会话备好上下文弹药
>
> 若用户未说明写作模式，先确认再决定是否跳过。
>
> **写作风格**：默认按文档类型设定基调（申报/可研＝严谨论证，投标/方案＝说服+结论先行，白皮书＝观点+趋势引导），用户可覆盖；每段提示词写明风格。这些提示词与平台无关，可直接粘到任意 AI（ChatGPT / DeepSeek 等）使用。

**步骤**：
1. 为大纲的每个最末级章节（或合并过小的章节）编写一段提示词
2. 每段提示词包含：
   - 章节号和标题
   - 字数限制
   - 写作要点（3-5 条具体指导）
   - 禁止事项（避免假大空、避免偏离主题）
   - 数据要求（需要引用的具体数据）
   - 插入图片标注位置
3. 甲方重点要求的章节（标注 ★）提示词要更详细，给出更多约束
4. 提示词末尾标注需要粘贴的原始素材路径

**提示词模板**：
```
请撰写"X.X 章节名"，约XXX字。

写作要求：
① ...（具体要点）
② ...

可用素材：[路径]

禁止：
- ...（具体禁止事项）
```

### 阶段 4：分模块写作

**目标**：产出所有文字素材 .md 文件到 `文字素材/` 目录

**开写前闸门**（用户说"准备好了"后、写第一个字之前必做。**"准备好了"只是声明，必须先核实，不能直接信**）：
- **先核对、如实回报差异**：对照 `素材准备清单.md` 查目录里**实际新增了什么**。**若没发现用户新增的素材、或仍有缺项 → 先明确告诉用户"没找到你准备的 X／以下 N 项仍缺"，绝不默默用 AI 生成或占位就往下写**。清单里早先标的"AI 可生成"只是备选项，**不等于现在就授权这么干**——仍要逐项问。
- **每个仍缺的项**〔选择〕让用户逐项定：① 我再去准备　② 改用 AI 生成（仅限可生成项）　③ 删掉相关内容　④ 暂时空着留占位（只能用户提供的项）。不擅自决定。
- **用户已交素材**：优先使用、原样使用；如需润色/精简，〔选择〕请用户先定（保持原样 / 同意你优化）
- 单份素材内有**错误/前后矛盾**，或多份素材**互相冲突**（金额/数量/口径不一致）→ 列出问题+给建议，〔选择〕让用户定夺（如"用 26 万／用 24 万／我再核"），不擅自取舍
- 以上全部处理完，再进入下面的写作步骤

**步骤**：
1. 〔选择〕**先让用户选择写作模式**：
   - **串行**：一个模块一个模块来（适合单个会话，可控）
   - **并行**：用户开多个会话，每个写一个模块（速度快）
2. 如果是并行模式，告知用户每个会话需要粘贴的上下文（写作任务指引.md + 该模块的提示词 + 素材）。**新会话启动提示词模板**：
   ```
   我在用 long-tech-proposal 流程写《项目名》的 module-XX。
   先读：[写作任务指引.md 路径]、[该模块提示词路径]；素材在 [路径]。
   请按提示词逐章写作，产出 .md 到 文字素材/module-XX/，严格遵守命名与字数。
   ```
3. 逐模块（或并行）生成 .md 文件
4. 每个 .md 文件头部的元信息**必须写成 HTML 注释**，这样 pandoc 不会渲染它（之前用可见标题/加粗写元信息，结果"所属模块/章节号/字数"全冒到正文里了）：
   ```markdown
   <!-- meta
   所属模块: module-XX
   对应大纲章节: X.X
   关键词: 逗号分隔
   引用图片: img_X-X_xxx.png
   -->
   # [章节标题]

   [正文从这里开始……]
   ```
   元信息只放注释里，正文紧接标题。**绝不要再用 `**所属模块**：` / `## 所属模块` 这类会渲染的可见行。**
5. 缺图片时用**不渲染的占位**：`<!-- 待补充图：xxx -->`，或一行文字 `（图：xxx，待补充）`。**不要用 `![xxx](待补充)`**——pandoc 会把它当图片框，缺图时只剩一个空表格框，很难看。
6. 文件命名严格遵循：`text_{章节号}_{内容简述}.md`

**注意事项**：
- 字数控制用"先写后量、再调整"：写完用字数统计核对，超出/不足超过 ±15% 时二次增删，不要空喊字数
- 表格用 Markdown 表格
- 数据注明来源
- 在合理位置标注图片插入点
- 如果一章太长，主动提示用户开新会话继续

### 阶段 5：图片与素材管理

**目标**：整理所有图片到 `图片素材/` 目录；图片需求与生图提示词已在阶段 2 的 `图片清单与生图提示词.md` 规划好，本阶段负责**落实**（重命名、归位、缺图回填/出图）

**步骤**：
1. 从已完成的所有 .md 文件中提取图片引用清单
2. 盘点已有图片，按命名规范重命名：

4. 对仍缺失的图片，对照并更新阶段 2 的 `图片清单与生图提示词.md`：

   - **架构图/流程图**：先检查是否装有 `arch-diagram` 技能——装了就建议直接用它出图，没装就只给绘制说明并提示用户"可安装 arch-diagram 技能，或用 AI 绘图工具照此说明出图"（不要默认用户已安装）
5. 如果用户有新图片，帮其放到正确目录并更新引用

### 阶段 7：文档合成

**目标**：将 .md 文件合成为排版完整的 .docx

**前置检查**：
- **先读参考、再动手（别凭记忆手搓排版）**：`references/pandoc-guide.md`（中文转换的 8 类坑及对策）+ `references/formatting-spec.md`（GB/T 9704 公文格式：字体/字号/页边距/三线表/标点）。reference.docx 一律用 `scripts/make_reference.py` 生成、后处理一律用 `scripts/apply_postprocess.py`——**不要自己重写样式逻辑，极易漏掉中文字体(eastAsia)、三线表、图片行高这些坑**
- 确认 pandoc 可用（`pandoc --version`），不可用则提示安装
- 确认 python-docx 可用（脚本依赖；`pip show python-docx`），缺则 `pip install python-docx`
- **文件完整性**：合成前核对所有应有的 .md 都存在且非空、章节齐全（并行写作后尤其要查），缺漏先补齐再合成
- 中间产物（merged.md / raw.docx）不覆盖源 .md，合成失败时按报错定位重跑即可，源文件不受影响

**合成流水线**：

```
文字素材/*.md → merged.md → fix_quotes.py → merged-clean.md
    → renumber_h3.py → merged-clean.md (修正编号)
    → pandoc + reference.docx → raw.docx
    → apply_postprocess.py → 初步排版.docx
```

**步骤**：

**7.1 确定排版标准 → 生成 reference.docx**

- **先定排版按哪套**（生成 reference 前必做，别默认就用预设）：
  - 若**阶段 0/1 用户已给模板/格式要求** → 直接按它来，不必再问（`strip_reference.py <模板.docx>` 提取样式，或按其字体/字号/页边距规格生成），并一句话告知"按你给的模板排版"
  - 否则 〔选择〕问用户：① **我有排版要求**（发模板 docx，或说具体字体/字号/行距/页边距）　② **用 Skill 预设**（下方默认）
- 据选择生成 reference.docx：
  - 用户的要求 → `strip_reference.py` 提取 或按规格调 `make_reference.py`
  - 预设 → `make_reference.py`；并 〔选择〕**版心**：① 通用 A4（默认，上下2.54/左右3.18cm，`make_reference.py ref.docx generic`）　② 严格公文版心（GB/T 9704：上37/下35/左28/右26mm，`make_reference.py ref.docx gb`——正式党政公文或评审要求公文格式时选）
- **Skill 预设排版标准**（无要求时用）：
  - 正文：仿宋 16pt（三号），行距固定28pt，首行缩进2字符
  - 一级标题：黑体 16pt 加粗
  - 二级标题：楷体 16pt 加粗
  - 三级标题：仿宋 16pt 加粗
  - 表格内容：宋体 10.5pt（五号），三线表格式
  - 图片题注：宋体 9pt，居中
  - 页边距：通用 A4 或公文版心（见上方〔选择〕）

**7.2 合并 Markdown**
- 将所有 .md 文件按章节顺序合并为 merged.md
- 同时把所有图片复制到 `成品/images/` 目录
- 更新 merged.md 中的图片路径为相对路径（`images/img_xxx.png`）

**7.3 预处理**
- **剥离残留元信息**：若有 .md 仍是旧式可见元信息（`**所属模块**` / `**章节号**` / `**字数**` / `**关键词**` / `**引用图片**` 等行，及其后孤立的 `---`），合并前删掉，别让它们进正文
- **清理缺图占位**：把 `![...](待补充)` 这类未提供的图片引用替换成 `（图：...，待补充）` 文本行，避免 pandoc 生成空图框
- 运行 `scripts/fix_quotes.py`：将 ASCII 引号替换为中文全角配对引号
- 运行 `scripts/renumber_h3.py`：统一 H3 编号格式（处理中文数字与阿拉伯数字混用）

**7.4 Pandoc 转换**
```bash
pandoc merged-clean.md \
  --reference-doc=reference.docx \
  --from=markdown+pipe_tables-implicit_figures \
  --to=docx \
  --toc --toc-depth=3 \
  --output=raw.docx
```
> **目录必须在这一步生成**：`--toc --toc-depth=3` 会插入可在 Word 内更新的目录字段。漏掉它就没有目录（这是之前"没目录"的原因）。生成后页码可能显示为待更新，提示用户在 Word 里「右键目录→更新域→更新整个目录」即可刷新页码。
> **`-implicit_figures` 不能少**：pandoc 3.x 默认会把"图片+图名"包进一个单元格表格框，缺图时只剩一个空表格框（之前"目录后莫名长表格"就是它）。关掉 implicit_figures 后，图片就是普通居中图，不再套表格框；图名如需显示，在 .md 里另起一行居中文字写。

**7.5 后处理**
- 运行 `scripts/apply_postprocess.py` 处理 raw.docx：
  - 统一图片宽度（默认 14.5cm）并居中
  - 清除图片段落的首行缩进
  - 表格改为三线表样式
  - 表格内容字体修正（表头黑体、正文宋体）
  - 标题段落清除缩进
  - 图片题注居中
- 输出初步排版完成的 .docx

**7.6 输出**
- 将排版完成的 .docx 放到 `成品/` 目录

**常见问题**：
- 图片被文字遮挡 → apply_postprocess.py 已处理，将图片段落行高改为 `auto`
- 图片不居中 → apply_postprocess.py 已处理，清除缩进+居中
- 引号退化 → fix_quotes.py 在 Pandoc 转换前预处理
- 标题字体跑偏 → 检查 reference.docx 是否正确设置了 Heading 1-3 的 east-asia 字体
> 以上只是高频项；**完整的 8 类问题与对策见 `references/pandoc-guide.md`——排版一出问题先查它，别自己猜。**

### 阶段 8：排版收尾

**目标**：补充封面、目录，输出最终文档

**步骤**：
1. 生成封面页，封面元素按文档类型不同：
   - 申报书：项目名称 / 承担单位 / 参与单位 / 申报日期
   - 投标文件：项目名称 / 投标人 /（报价、招标编号按招标文件要求）/ 日期
   - 技术方案书：项目名称 / 编制单位 / 客户单位 / 版本 / 日期
   - 可研 / 白皮书：标题 / 编制单位 / 日期
2. 目录已在阶段 7.4 由 `--toc` 生成、位于文档最前。**用 `scripts/add_cover.py` 把封面插到目录之前**（pandoc 没法让封面先于目录，必须后处理插入），得到正确顺序 封面 → 目录 → 正文：
   ```bash
   python scripts/add_cover.py 成品/初步排版.docx 成品/最终文档.docx "项目标题" "承担单位：XXX" "二〇二六年X月"
   ```
   提示用户在 Word 内「右键目录→更新域」刷新页码。
3. 最终检查（逐项核对，发现不对就修，别只生成不检查）：
   - 正文字体字号是否正确（仿宋 16pt；若显示成默认字体，多半是 reference.docx 没生效或 apply_postprocess 没跑）
   - 目录是否存在、层级是否到三级
   - 全文页码是否正确
   - 封面信息是否完整
   - 所有图片是否正常显示
4. 〔选择〕问用户是否需要调整（字体大小 / 页边距 / 封面样式 / 不用调）
5. 输出最终文档
6. **提示用户**：旧版本移入 `09-archive/` 目录
7. **明确告知**：AI 排版输出的是初稿，正式提交前建议人工过一遍（封面美化、分页、甲方特殊格式细节）

## 文件命名规范

| 类型 | 格式 | 示例 |
|------|------|------|
| 文字素材 | `text_{章节号}_{内容简述}.md` | `text_1-1_承担单位概况.md` |
| 图片素材 | `img_{章节号}_{内容简述}_{序号}.ext` | `img_4-1_总体技术架构图_v1.png` |
| 会议纪要 | `YYYY-MM-DD_主题.docx` | `2026-05-17_需求讨论.docx` |
| 需求变更 | `change_YYYYMMDD_简述.docx` | `change_20260517_新增摄像头.docx` |

> **命名总则**：面向用户的产物（大纲、清单、提示词、说明、最终文档）一律**中文命名**，方便用户在文件夹里直接找到；只有**图片文件**和 **pandoc 构建中间产物**（merged.md / reference.docx / raw.docx 等）因技术原因用英文。

## 进阶：如何处理超大文档

当文档预估超过 60 页时：
1. **分模块写作**：每个模块（3-6 个 md 文件）独立写作
2. **跨会话继续**：一章写不完时，在新会话中说"继续写 module-XX，先读 写作任务指引.md"
3. **合成阶段独立**：写作阶段的会话不负责合成，另开会话做合成
4. **后处理脚本化**：排版问题通过脚本一次处理，不手动逐项修改

## 捆绑脚本说明

`scripts/` 下的脚本都接受命令行参数，可以独立运行：

| 脚本 | 用途 | 用法 |
|------|------|------|
| `make_reference.py` | 生成带中文字体的 reference.docx | `python make_reference.py output.docx` |
| `strip_reference.py` | 从已有 docx 提取样式到 reference.docx | `python strip_reference.py source.docx reference.docx` |
| `fix_quotes.py` | ASCII 引号→中文配对引号 | `python fix_quotes.py input.md [output.md]` |
| `renumber_h3.py` | 统一 H3 编号格式 | `python renumber_h3.py input.md output.md` |
| `apply_postprocess.py` | docx 后处理（图片/表格/字体） | `python apply_postprocess.py raw.docx output.docx` |
| `add_cover.py` | 把封面页插到目录之前 | `python add_cover.py in.docx out.docx "标题" "副行1" …` |

这些脚本依赖 `python-docx` 库。如果用户环境未安装，运行 `pip install python-docx`。

> **直接调用这些脚本，不要在会话里另写一套。** 它们已封装好中文字体(eastAsia)、三线表、图片行高、引号、标题编号等一堆坑的正确处理；临时手搓几乎必踩坑——本项目就因为字体设置位置写错，导致正文/标题中文字体全丢过。要改排版逻辑就改脚本本身，而不是绕过它。
