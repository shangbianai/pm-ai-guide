Document Automation

一键输出
可评审的 BRD / MRD 文档

把业务资料、市场判断、竞品信息和产品想法，压进一套稳定的 Skill 工作流，输出高质量、可使用、符合你规范和偏好的商业与市场文档。

这节课的目标：让 AI 不再只会“写得像文档”，而是能交付一份可以拿去讨论、评审和继续修改的 BRD/MRD。
BRD回答“为什么做、值不值得做”
MRD回答“市场要什么、做什么能赢”
Skill固化角色、流程、方法论和模板
PDF课后资料与评审材料可直接分享
拒绝 AI 味道 遵循文档规范 支持实操演示
Why It Matters

很多 BRD/MRD 的问题，不是“字不够多”，而是判断不够硬

普通 AI 写法

  • 标题很完整，但结论泛泛而谈
  • 市场分析像百科摘要，缺少边界
  • 用户痛点没有优先级和证据链
  • BRD/MRD/PRD 的关注点混在一起
  • 每次输出版式和质量都不稳定

Skill 工作流写法

  • 先定义文档目的和受众
  • 用 BRD/MRD 框架约束章节和判断
  • 用 TAM/SAM/SOM、SWOT、RICE 等模型支撑结论
  • 用脚本和 HTML 模板固定交付格式
  • 输出后可以继续沉淀成团队规范
BRD vs MRD

BRD 和 MRD 不是两种格式，而是两种决策问题

BRD 面向资源投入和立项判断，MRD 面向市场需求和产品方向。你要先问清楚“谁看这份文档、用它做什么决策”，再决定输出哪一种。

一句话记忆：BRD 争取资源，MRD 锁定机会。

BRD · Business

核心问题：为什么现在做？值不值得投？

  • 商业价值与 ROI
  • 市场规模与商业模式
  • 资源需求与风险评估
  • 面向高管、业务负责人、投资人

MRD · Market

核心问题：市场要什么？怎么做才能赢？

  • 用户需求与痛点优先级
  • 竞品和替代方案
  • 产品建议与 GTM 策略
  • 面向产品、技术、市场团队
Skill Anatomy

`brd-mrd-master` 的本质：把文档生产变成一个可复用系统

角色

资深产品经理 + 商业分析师，默认用评审视角写文档。

输入

产品、行业、文档类型、资料、受众和背景信息。

方法论

BRD/MRD 章节、TAM/SAM/SOM、SWOT、RICE、用户画像。

交付

AI 生成结构化 JSON，脚本渲染成 HTML 报告，再导出 PDF。

关键变化：AI 负责分析和结构化内容，模板负责版式和一致性，脚本负责最终交付。
File Structure

一个好 Skill，至少有说明书、方法论、模板、脚本

这一节的 Skill 包不是靠一次性 prompt 取胜，而是把“怎么分析”和“怎么呈现”拆开维护。

skills/brd-mrd-master/
├── SKILL.md
│ # 角色、输入、流程、输出约束
├── reference/
│ ├── brd-guide.md
│ ├── mrd-guide.md
│ └── industry-analysis-framework.md
├── assets/
│ └── report-template.html
└── scripts/
└── generate-report.py
Input Design

想让文档不像 AI 写的，第一步是给它真实业务约束

必须输入

  • `PRODUCT`：产品/项目名称和简介
  • `INDUSTRY`：行业与市场范围
  • `DOC_TYPE`：BRD / MRD / BOTH

强烈建议

  • `MATERIALS`：业务资料、访谈、报告
  • `PURPOSE`：立项、规划、融资或合作
  • `AUDIENCE`：高管、业务方或产品团队

最好补充

  • 已有资源和限制
  • 竞品名单和内部判断
  • 公司偏好的文档结构和表达风格
资料越贴近真实项目，AI 越不容易写成“正确但没用”的通用稿。
Workflow

从一堆资料到一份文档：中间要经过5 个稳定步骤

1定义任务明确产品、行业、文档类型和受众。
2提取材料从业务资料里抽取事实、数据、限制和假设。
3框架分析套入 BRD/MRD 章节和行业分析模型。
4结构化输出生成符合模板字段的 JSON 数据。
5脚本渲染用模板生成 HTML，再导出 PDF 文档。
Anti AI Flavor

拒绝 AI 味道，不是靠“语气更像人”，而是靠结构化交付

如果让模型直接写整份 HTML，它会同时承担分析、排版、字段组织和视觉一致性，任何一环都可能漂移。

更稳的方式：模型只产出内容数据，模板和脚本负责样式。
输出质量控制 HTML Template
内容
执行摘要、市场分析、商业模式、功能规划、风险与指标
格式
统一标题层级、卡片组件、表格、指标和章节节奏
检查
字段缺失可以回查，章节缺口可以补齐，模板可以持续复用
交付
HTML 可演示，PDF 可归档，后续可接入团队文档规范
BRD Spine

BRD 的 10 章，其实是在回答一个问题：这事值不值得投？

1. 执行摘要30 秒让决策者知道结论和行动。
2. 项目背景为什么现在必须做，不做有什么代价。
3. 市场分析市场多大、谁在玩、趋势往哪走。
4. 商业模式怎么赚钱，多久能回本。
5. 产品定位卖给谁，解决什么，凭什么选我们。
6. 功能规划MVP 先做什么，后面怎么扩展。
7. 运营策略怎么获客，怎么增长，谁能合作。
8. 风险评估可能怎么失败，提前怎么处理。
9. 资源需求要多少人、多少钱、多长时间。
10. 成功指标用什么指标判断它真的做成了。
MRD Spine

MRD 的 7 章骨架，是从市场事实推导产品方向

1. 执行摘要一句话说清市场机会、核心发现和下一步建议。
2. 市场机会评估用容量、增速、渗透率判断市场是否值得进入。
3. 用户需求分析明确画像、核心需求和高优先级痛点。
4. 竞品分析对比直接竞品、间接竞品和替代方案，找到机会缺口。
5. 产品建议把市场证据转成功能优先级、体验建议和技术方向。
6. GTM 策略建议说明定价、渠道、推广和进入市场路径。
7. 数据支撑交代行业数据、调研证据和市场预测模型。
这里的“7”指七个章节，不是七张页面。MRD 的好坏，不看“写了多少功能”，而看功能建议是否来自市场证据和用户痛点。
Demo Case

实操案例可以这样跑：口腔连锁 AI 线索转化系统

沿用前两节市场洞察的业务语境，把零散资料进一步变成 BRD/MRD 文档。这样学员能看到：洞察报告不是终点，它可以继续转化成立项材料和产品规划材料。

同一批市场资料，可以先生成洞察报告，再生成 BRD/MRD，再继续拆 PRD 和路线图。

输入材料

  • 客户访谈摘要
  • 业务痛点：线索浪费、转化慢、跟进不稳定
  • 竞品和替代方案
  • 公司已有销售和运营资源

输出目标

  • BRD：是否立项、资源怎么投
  • MRD：市场机会和产品方向
  • HTML：可演示、可修改
  • PDF：可分享给团队和学员
Prompt Pattern

调用 Skill 时，不要只说“帮我写 BRD”

请使用 brd-mrd-master Skill，基于以下资料生成 BOTH 类型文档：
PRODUCT：口腔连锁 AI 线索转化系统
INDUSTRY：口腔医疗服务 / 本地生活获客与转化
DOC_TYPE：BOTH
PURPOSE：内部立项评审 + 产品规划讨论
AUDIENCE：业务负责人、产品团队、运营负责人
MATERIALS：访谈摘要、业务痛点、竞品资料、上一节市场洞察报告
要求：先输出结构化 JSON，再调用 scripts/generate-report.py 生成 HTML 报告。
提示词越像“项目说明书”，生成结果越像真实产品文档；提示词越像一句愿望，生成结果越像 AI 作文。

What To Watch

看完这一节，学员应该记住 3 个判断

文档不是越厚越好

BRD/MRD 的价值在于让团队更快做决策，而不是堆满正确废话。

Skill 不是提示词

它把角色、流程、方法论、模板和脚本一起固化，质量才稳定。

模板让风格归一

团队可以把自己的规范沉淀进模板，让 AI 更像内部同事。
