# Web 电商后台原型

## 工作方式

先识别业务场景、目标用户、核心任务、页面范围和现有项目技术栈。缺少非关键细节时写明假设并继续；不擅自更换用户指定的行业或框架。已有项目先检查入口与组件，再局部迭代。

没有项目时默认输出可本地打开的 HTML/CSS/JavaScript 原型。使用明确标注的模拟业务数据，不要求数据库、API 密钥或真实账号。登录、支付、退款等仅模拟，不接入真实服务。

先列出页面、核心流程和状态，再完成可操作原型。原型评审关注结构、流程闭环、数据一致性，不能用静态截图或无反馈按钮替代交互。迭代字段时同步检查列表、详情、筛选、表单和状态。

## 课程参考资料

- 设计业务对象和页面时，按当前端读取 [项目规则](references/项目规则.md) 中对应小节。商品、订单、会员、活动、门店是咖啡零售案例的对象；其他行业应替换为用户的业务模型。
- 需要整理需求输入时参考 [提示词模板](references/提示词模板.md)。只生成本次要求的端，不因模板同时列出两端而扩大任务。
- 交付前按范围检查 [验收清单](references/验收清单.md)，记录不适用项和未验证项，不把清单当成已有示例完成全部功能的证明。

## 交付与验证

交付原型入口、所需本地资源、使用说明、项目规则和验收结果；用户需要打包时包含全部依赖。说明哪些数据为模拟、哪些功能只是交互示意、刷新是否重置状态。

检查主流程、导航返回、空态与异常态，检查数据变更后的金额/数量/状态一致性。可用浏览器时实际点击验证；不可用时如实说明静态检查的局限。未经验证不要声称所有功能已完成。

## Web 后台设计重点

以运营总览、商品、订单、会员、活动、门店作为零售案例的功能候选，按需求选择。后台独立于移动端交付；若同时涉及两端，保持字段与状态口径一致，不假装两个静态文件共享后端。

采用可收纳的侧边导航、顶部操作区、筛选区、数据表格和右侧详情抽屉。总览集中展示全局指标；商品、订单、会员等模块应根据业务任务采用不同布局，避免只换标题和数据。

商品示例覆盖分类、价格、库存和上下架；订单覆盖履约状态与异常处理；会员覆盖分层与历史记录。新增、编辑、筛选、批量操作必须有可观察结果，并明确数据是否仅保存在内存。

状态流转先定义允许的前后状态；筛选后批量操作只作用于选中对象。处理空结果、无选择和输入错误；模拟导出需输出文件或明确说明暂未实现，不能用成功提示冒充完成。
