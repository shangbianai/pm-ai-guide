PRD Writing

需求文档不是“写出来”，而是结构化沉淀

这一节讲如何基于原型、流程图、业务资料和参考模板，让 AI 生成一份能评审、能开发、能测试、能验收的 PRD。

核心目标：用模板去除 AI 味道，让文档回到业务规则、页面元素、流程和验收标准。
修订记录版本、修订章节、原因、确认人
功能详细说明功能描述、业务流程、页面元素、业务规则
验收标准前置条件、操作步骤、预期结果
01:30 - 04:00
Problem

没有模板，AI 很容易写成“漂亮废话”

AI 默认会写概述、价值、亮点，但真实 PRD 需要的是：字段、状态、规则、流程、异常、权限、上线下线和验收标准。

泛泛文档

  • 背景很长，规则很少
  • 没有页面元素表
  • 异常流程缺失
  • 无法指导研发测试

可交付 PRD

  • 结构清晰
  • 规则可执行
  • 字段可开发
  • 标准可验收
04:00 - 07:00
结构来源

这份模板参考了三类真实文档结构

功能需求说明书

重点吸收：修订记录、适用范围、名词解释、需求详细说明、业务流程、界面描述、页面元素、管理规则。

传统 PRD

重点吸收：概述、目标、Roadmap、风险、功能需求、非功能需求、上线下线、运营计划、跨部门评审。

商业需求文档

重点吸收：文档目的、范围、读者、问题、解决方案、市场、竞争、商业模式和风险约束。

07:00 - 10:00
Structure

完整 PRD 至少要有这 12 块

模板的价值，是让 AI 不再随意发挥，而是按固定结构补齐产品经理需要的判断。

1-4文档信息、修订记录、文档说明、背景与目标
5-8用户场景、业务流程、功能总览、功能详细说明
9-12数据接口、非功能需求、上线下线、评审清单和待确认问题
10:00 - 13:00
Page Elements

页面元素表，是 PRD 从“说明”变成“可开发”的关键

序号页面区域数据项/控件类型/输入方式是否必填校验/管理规则输出/联动
1查询区创建时间日期区间否未输入时默认展示全部刷新列表
2列表区状态自动回显是按业务状态流转影响操作按钮
3操作区提交按钮是必填项校验通过后可提交进入审批流程
13:00 - 16:00
Rules

业务规则和业务逻辑，要写得可执行

规则回答“什么情况下能不能做”，逻辑回答“系统怎么判断、怎么变更状态、怎么写数据”。

判断条件、状态流转、异常处理和责任方都要落到表格里。

业务规则

  • 权限规则
  • 额度/数量/时间限制
  • 审批条件
  • 异常兜底

业务逻辑

  • 字段校验
  • 接口调用
  • 状态变更
  • 消息通知
16:00 - 18:30
原型承接

原型做好之后，可以直接让 AI 生成 PRD 初稿

Cursor、Codex、Claude Code 或 IDE 工具做出的原型，本质上已经包含页面、控件、流程和交互状态。下一步不是重新写一遍，而是让 AI 先读取原型结构。

推荐顺序：先让 AI 提取页面清单、功能清单、交互路径和状态变化，再进入 PRD 模板。
原型文件页面、组件、按钮、表单、状态、路由
AI 结构提取页面清单、功能模块、用户路径、异常状态
PRD 初稿背景、流程、页面元素、业务规则、验收标准
18:30 - 21:00
模板优先

直接生成可以很快，但套模板才稳定

直接让 AI 写 PRD，往往能拿到一版“看起来完整”的文档；但如果没有模板约束，它很容易漏掉页面元素、异常规则、权限、验收标准和待确认问题。

直接生成

  • 速度快
  • 适合粗略草稿
  • 结构容易漂移
  • 细节依赖模型发挥

参考模板生成

  • 结构稳定
  • 字段和规则更完整
  • 更容易人工校准
  • 可沉淀为团队标准
21:00 - 24:00
工作流

从原型到 PRD：推荐 6 步

1. 准备资料

原型、流程图、会议记录、需求池、业务规则。

2. 读取结构

让 AI 先列页面、功能、角色和流程。

3. 套模板

按 PRD 模板补齐章节。

4. 补表格

页面元素、业务规则、状态、验收标准。

5. 列问题

缺失信息放入待确认问题。

6. 人工校准

产品经理确认范围、规则和优先级。

24:00 - 27:00
PRD Skill

把模板做成 Skill，才能稳定复用

PRD 文档生成 Skill（prd-doc-writer）把模板、写作流程和质量检查封装起来，让 AI 每次都按同一套结构输出 PRD。

skills/prd-doc-writer/ ├── SKILL.md └── references/ ├── PRD文档模板.md └── PRD质量检查清单.md
27:00 - 30:00
提示词

实操时可以这样输入

把资料路径、原型路径、关注点和不做范围写清楚，AI 才能稳定输出。

请使用 PRD 文档生成 Skill（prd-doc-writer），基于以下资料生成 PRD： 产品/系统名称： 需求名称： 业务背景： 原型路径： 流程图路径： 参考资料路径： 本期范围： 不做范围： 要求： - 严格按 PRD 模板输出 - 每个功能必须有页面元素表、业务规则表、验收标准 - 信息不足的地方放入待确认问题
30:00 - 33:00
检查清单

一份 PRD 有没有 AI 味，看这 8 个点

检查项合格标准
结构章节完整，能覆盖评审、开发、测试和上线
范围明确本期做什么、不做什么
流程主流程、异常流程、状态流转清楚
页面页面元素、字段、控件、校验、联动完整
规则判断条件可执行，不是抽象描述
验收有前置条件、操作步骤、预期结果
风险列出约束、依赖、待确认问题
语言少口号，多表格、规则、状态和事实
33:00 - 34:30
回顾重点

回顾重点：这节课能获得什么

第一，知道完整 PRD 应该有哪些结构。

第二，掌握从原型到 PRD 的 AI 工作流。

第三，拿到一份可复用的 PRD 模板和 Skill。

接下来进入实操环节：用参考模板和 Skill，把业务资料转成一份完整 PRD。

一句话带走

PRD 的专业感，不来自篇幅，而来自结构、规则、流程和可验收的细节。
