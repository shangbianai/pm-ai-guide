WHY

为什么这节不是普通的文本分析？

真正有价值的是把用户反馈接进业务系统，让 AI 在真实流程里完成结构化分析，而不是让人复制粘贴一段吐槽。

  • 入口真实：用户在页面提交反馈，系统生成记录。
  • 数据可追踪：飞书多维表格保留每条反馈和处理状态。
  • 动作闭环：AI 更新字段、生成回复草稿，并通知团队。

减少人工搬运

不需要手动复制反馈给 AI，再复制回表格。

统一判断标准

分类、优先级和回复口径都通过方法论约束。

沉淀需求池

每条反馈都能进入可筛选、可复盘的数据表。

及时通知

处理结果自动发到群里，方便团队协同。

ARCHITECTURE

系统链路：从用户提交到团队通知

这个案例最值得学的是链路设计：页面只是入口，真正的价值在后面的自动化处理。

1

用户提交反馈

前端表单收集昵称、邮箱和反馈内容，通过 POST /api/feedback 进入后端。

2

写入飞书多维表格

后端创建新记录，先保存原始反馈和“未处理”状态。

3

触发 OpenClaw Agent

服务端执行 openclaw agent --agent main --message，把记录 ID、反馈内容和处理方法论交给 Agent。

4

更新字段并通知群聊

Agent 分类、提炼痛点、判断优先级、写回复草稿，并把结果发到飞书群。

FIELDS

飞书字段决定 AI 能不能形成需求池

字段设计不是表格细节，而是决定反馈能不能被筛选、排序和后续跟进。

字段作用AI 处理重点
用户吐槽的内容保存原始反馈识别真实痛点，不只复述原话
AI 解析状态标记处理进度从未处理更新为已处理
反馈分类区分需求、体验、Bug 等功能需求 / 体验问题 / Bug反馈 / 性能问题 / 其他建议
核心痛点沉淀可讨论问题用 1-2 句话提炼背后需求
优先级支持后续排序高 / 中 / 低，说明业务影响
AI 拟定回复草稿辅助用户运营共情、表态、临时方案、后续跟进

CASE

模拟测试：一条反馈如何变成需求

可以用这条反馈测试完整链路：提交表单，看飞书记录、AI 字段和群通知。

昵称：林可
邮箱：linke@example.com
反馈内容：
我每次想查历史反馈都很麻烦，只能一页页翻。我们客服同事经常需要按用户、关键词和处理状态筛选，但现在没有搜索和筛选入口，导致回复客户前要花很多时间找记录。希望能加一个搜索框和状态筛选。

预期分类

功能需求，偏“反馈记录检索效率”。

核心痛点

历史记录缺少检索和状态筛选，客服跟进效率低。

优先级判断

如果客服高频使用，可判为中到高优先级。

SUMMARY

回顾重点：这节课的价值

这节课要带走的不是一段代码，而是一种思路：把 AI 放进真实产品接口，让反馈自动进入需求处理链路。

  • 产品入口负责收集真实反馈。
  • 数据表负责保存状态和结构化结果。
  • Agent 负责按照方法论分析并触发后续动作。

从文本到结构

把自然语言反馈变成字段。

从分析到动作

不止输出结论，还更新记录和通知团队。

从单次到系统

让反馈处理变成可复用流程。
