Lesson Goal

这节课解决一个 PM 高频问题

现实里的需求输入很少是干净的：客户访谈、群聊截图、老板口头补充、销售反馈，常常混在一起。

这个 Skill 的核心价值，是把混乱输入转成功能清单、需求池和版本决策记录。

一句话：让 AI 帮你把“用户说了什么”整理成“产品到底要做什么”。

本节课最终交付

Mode A第一次整理：从零建立功能清单和需求池
Mode B新需求进来：评估冲突、影响并更新版本
4维覆盖度、业务影响、紧迫程度、技术风险
5类接受、推迟、合并、拒绝、待确认
Why Skill

为什么需求整理不能只靠普通摘要？

普通摘要会把所有声音压成“客户想要什么”。但产品经理真正要判断的是：这是真需求吗？谁提的？解决什么场景？值不值得进当前版本？

普通总结的问题

  • 所有需求看起来都重要
  • 重复需求被反复讨论
  • 口头需求没有来源记录
  • 拒绝的需求没有留痕

Skill 固化的判断

  • 真伪与质量校验
  • KANO 分类
  • 四维度评分
  • 冲突和范围蔓延提醒

PM 要抓住什么

  • 用户故事是否成立
  • 验收标准是否可量化
  • 是否影响当前版本边界
  • 最终仍由 PM 决策
How To Use

实操前先知道：怎么安装、怎么调用？

把 `pm-requirements` 放进 Claude Code 的 skills 目录后，在对话里明确说“使用 pm-requirements skill”，再提供客户访谈、用户反馈或业务方需求。

触发词很自然：需求整理、功能清单、需求池、新需求进来了、需求变了、做 PRD。

First Prompt

第一次使用：直接把材料交给 Skill

你不需要把需求提前整理干净。真实工作里，客户文档、会议纪要、口头补充可以一起输入，让 Skill 先做解析、归类和排序。

关键是告诉 AI：这是第一次整理，需要输出功能清单和需求池。

Two Modes

这个 Skill 最关键：自动区分两种模式

它执行前会先检查 `_pm_context/requirements/feature-list.md` 是否存在。没有就初始化，有就进入增量更新。

1解析输入从文档、聊天、口头补充里提取功能点、场景、痛点。
2归类校验KANO 分类，检查真实性、价值和一致性。
3评分排序按覆盖度、业务影响、紧迫程度、技术风险打分。
4输出文件生成 feature-list.md 和 requirement-pool.md。
5确认文档确认后生成 Word / Excel 版本。
1读取现状读取已有功能清单和需求池。
2理解新需求提取描述、提出人、背景和紧迫程度。
3影响分析判断无冲突、增强、重复、冲突或范围蔓延。
4处置建议接受、推迟、合并或拒绝。
5版本更新更新需求池，必要时升级 feature-list 到 v1.1。
Quality Gate

先判断真伪，再进入优先级排序

这个 Skill 不会把所有声音都当成需求。它会先做质量校验：有没有角色、场景、行为、结果，有没有价值信号，有没有定位冲突。

真实性

是否能识别出用户、场景、行为和结果。缺失就标记待确认。

价值性

是否有可衡量指标、受益规模、发生频率。价值不明不硬排优先级。

一致性

是否重复、范围蔓延或与产品定位冲突。冲突必须提示 PM 决策。

重点：AI 可以给建议，但不能替 PM 偷偷把冲突藏起来。
Priority Matrix

优先级怎么排：四个维度共同打分

评分不是凭感觉，而是把用户覆盖度、业务影响、紧迫程度和技术风险放到同一张表里。

维度权重核心问题例子
用户覆盖度30%多少用户、多高频使用？所有门店每天都要录入。
业务影响30%对收入、效率、体验影响多大？减少总部统计时间和出错率。
紧迫程度20%现在不做损失多大？库存断货已经反复发生。
技术风险20%实现难度和依赖风险多高？是否依赖外部 API 或复杂集成。
P0 不是越多越好：Skill 约束 P0 不超过总功能数的 30%。
Outputs

最终输出：功能清单 + 需求池

这个 Skill 的交付物不是聊天窗口里的一段答案，而是一套可以持续维护的需求资产。

feature-list.md功能清单源文件，始终保持最新版本。
requirement-pool.md需求池源文件，记录所有进入评估的需求。
功能清单_vX.X.docx团队日常阅读和评审用的 Word 版本。
功能概览表_vX.X.xlsx功能概览和需求池的表格版本。
需求池.xlsx持续追加的需求流水表，拒绝和推迟也记录。
Feature List

功能清单不是功能名列表

每个功能都要写成用户故事，并给出可验证的验收标准。这样后面写 PRD、评审和排期才有基础。

模板要求：作为 X，我需要 Y，以便 Z。
### F-001：门店销售数据录入 - 用户故事：作为门店店长，我需要录入每日营业额、客单价和翻台率，以便总部及时掌握经营情况。 - Kano 类型：基本型 - 优先级：P0 - 综合评分：4.6 - 归属版本：v1.0 - 验收标准： - [ ] 店长可在手机端完成当日数据录入 - [ ] 总部可按门店和日期查看汇总 - [ ] 数据支持导出 Excel - 依赖：用户登录、门店权限
Requirement Pool

需求池的价值：把“为什么不做”也记录下来

很多团队的问题不是没有需求，而是同一个需求每周都被重新讨论。需求池记录来源、状态、处置意见和归属版本，减少反复扯皮。

需求提出人类型处置备注
会员积分系统张总新功能已推迟有价值，但超出 v1.0 门店经营核心范围。
美团订单同步张总集成待确认依赖美团 API，可先进入需求池。
微信小程序看数据老板移动端已接受作为移动端方案之一，服务核心看板。
用友财务打通财务集成已推迟技术依赖高，建议 v2.0 评估。
Incremental Update

新需求来了：不要重写，做增量评估

当 `feature-list.md` 已存在，Skill 会进入 Mode B：读取现有功能清单，判断新需求是新增、合并、重复、冲突还是范围蔓延。

这一步最像真实产品工作：不是收集需求，而是维护需求体系。

合并

“代打卡”并入考勤打卡，但要补数据真实性规则。

升级

“按财务模板导出”升级原来的数据导出功能。

新增

“差评预警”新增，但依赖美团/点评数据接口。

影响范围

“跨门店排班”会影响排班和员工数据模型。

Advantages

这个 Skill 好在哪里？

它不是替 PM 做最终决定，而是把混乱输入、隐含需求、冲突关系和优先级依据整理出来，让 PM 决策更稳。

从乱到清

把聊天、文档、口头补充统一成结构化功能清单。

从一次性到持续

需求池持续追加，版本变更有痕。

从主观到有依据

评分维度明确，P0 不再全靠拍脑袋。

从隐藏冲突到显性决策

重复、冲突、范围蔓延都会被标出来。

从功能名到用户故事

每个功能都有场景、目标和验收标准。

从老板一句话到需求资产

拒绝、推迟和待确认也进入需求池。
